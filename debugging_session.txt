● Multi-Day Debugging Session: CloudFront → Lambda@Edge → rag-node

  The Goal

  Wire up a working chatbot pipeline: Browser → CloudFront distribution (E26BC41QUBWZIN) → Lambda@Edge
  signer → rag-node Lambda → SSE streaming response. The chatbot frontend at genious-jay.jaymuntz.com
  had been returning 403 Forbidden on all /api* requests.

  ---
  Phase 1: Lambda Function URL with AWS_IAM Auth

  Initial architecture: The signer was supposed to SigV4-sign requests and forward them to the rag-node
  Lambda Function URL (AuthType: AWS_IAM).

  The first working piece: an admin IAM user (BedrockCourseUser with AdministratorAccess) could invoke
  the Lambda Function URL directly and get a 200. So the URL and rag-node itself were fine.

  Problem: Lambda@Edge signer role couldn't invoke it — 403 every time.

  Investigation: Tried every resource policy Principal variant:
  - Principal: * — 403
  - Principal: arn:aws:iam::666781058351:root (account root) — 403
  - Principal: arn:aws:iam::666781058351:role/genious-jay-rag-signer-role (exact role ARN) — 403

  The IAM policy simulator reported "allowed" for all of these, which was actively misleading.

  Root cause discovered: Lambda@Edge functions are executed by edgelambda.amazonaws.com, which assumes
  the execution role with a service-level session policy that restricts the permissions of the resulting
  session. This session policy does not include lambda:InvokeFunctionUrl. Because session policies are
  a ceiling on what the identity policy can grant, no identity-based or resource-based policy change
  could fix this. The policy simulator doesn't model session policies from assumed-role contexts, which
  is why it showed "allowed" while actual calls failed.

  ---
  Phase 2: Trying to Bypass the Function URL Problem

  Attempt: AuthType: NONE

  Removed auth from the Lambda Function URL entirely, thinking we could just call it without signing.
  Immediately hit an account-level restriction — all AuthType: NONE Lambda Function URL access was
  blocked regardless of any policy. Confirmed with a dedicated test Lambda (url-auth-test). This is
  likely an SCP applied at the AWS organization or account level.

  Attempt: CloudFront OAC for Lambda URLs

  AWS documentation and blog posts describe using an Origin Access Control (OAC) to have CloudFront
  natively sign requests to Lambda Function URLs — no Lambda@Edge signer needed at all. Created OAC
  E2Y8LB3CB3ULDI and attached it to the CloudFront origin.

  This failed in an unexpected way. CloudFront OAC for Lambda URL origins constructs its SigV4 canonical
  request using UNSIGNED-PAYLOAD as the body hash, but the Lambda URL verifier computes and checks the
  actual SHA-256 hash of the request body. The signatures never matched. Error: "The request signature 
  we calculated does not match the signature you provided." The AWS blog post implying this would work
  was incorrect for this auth type combination.

  Attempt: AuthType: NONE + OAC

  Tried keeping OAC for the signing but AuthType: NONE for the URL auth — still hit the account-level
  block.

  ---
  Phase 3: The Breakthrough — Direct Lambda API Invocation
  
  Key insight: The Lambda@Edge session policy blocks lambda:InvokeFunctionUrl but says nothing about
  lambda:InvokeFunction. These are completely different IAM actions. Instead of hitting the Function URL
  endpoint, the signer could call the Lambda API directly:

  POST https://lambda.us-east-1.amazonaws.com/2015-03-31/functions/genious-jay-rag-node/invocations

  This is a standard AWS API call with SigV4 signing against the lambda service. Switched the signer
  code to call this endpoint instead. Got a 200 response for the first time.

  New problem — wrong event format (signer v6):

  Direct Lambda API invocation passes the request body as the Lambda event object. rag-node's index.mjs
  is written to handle HTTP events (Lambda Function URL format), where it reads event.body and parses
  JSON from it. When the signer was sending {"question":"hello"} directly, rag-node received that as the
  event — with no body field — and couldn't parse the question.

  Fix: Wrap the viewer's request body before invoking:

  const lambdaEvent = { body: viewerBody.toString('utf-8') };
  const invokePayload = Buffer.from(JSON.stringify(lambdaEvent));

  New problem — response format (signer v7):

  rag-node uses awslambda.streamifyResponse, which is designed for true streaming via a Lambda Function
  URL. When invoked through the buffered lambda:InvokeFunction API instead, it returns its response in a
  packed binary format:

  {"statusCode":200,"headers":{...}}\x00\x00...\x00data: {"type":"chunk"...}\n\ndata: {"done"...}

  The SSE body is appended after the prelude JSON and null-byte padding. Added extractSseBody() to find
  the end of the prelude (}}), skip past the null bytes, and return only the SSE portion. The signer
  then returns this as a text/event-stream response to CloudFront.

  ---
  Phase 4: Final Deployment Fixes
  
  v8 — Blacklisted header (502 error):

  The signer was returning x-accel-buffering: no as a response header. CloudFront's Lambda@Edge
  validator rejected this (it's an Nginx-specific directive that CloudFront blacklists). Response: 502
  "The Lambda function result failed validation: The function tried to add a blacklisted header."
  Removed the header.

  v9 — Timeout (503 error):

  "hello" worked fine, but any real question (triggering Bedrock knowledge base retrieval + LLM
  generation) returned 503 "The Lambda function is invalid or doesn't have the required permissions."
  The actual cause was the signer Lambda's timeout: 5 seconds. Bedrock queries take 10–20+ seconds.
  CloudFront's error message was misleading — it shows a permission-sounding error for Lambda timeouts
  too.

  Lambda@Edge origin-request functions support up to 30 seconds. Updated the signer to 30s timeout,
  256MB memory, and published v9. Real queries now return full responses.

  ---
  Key Lessons

  1. Lambda@Edge session policies are invisible to IAM policy simulator. The simulator models identity +
  resource policies but not session-level restrictions applied by edgelambda.amazonaws.com. Always test
  actual invocation from the Lambda@Edge context.
  2. lambda:InvokeFunctionUrl and lambda:InvokeFunction are separate IAM actions. Lambda@Edge session
  policy blocks the former but not the latter. Direct API invocation is a viable workaround.
  3. CloudFront OAC + Lambda Function URL has a SigV4 payload hash mismatch. OAC sends UNSIGNED-PAYLOAD
  but Lambda URL auth checks the real hash. This combination doesn't work.
  4. awslambda.streamifyResponse returns a packed format over buffered invocation. The prelude JSON +
  null bytes must be stripped to recover the SSE body when calling via InvokeFunction instead of the
  streaming Function URL.
  5. CloudFront 503 "doesn't have required permissions" also fires on timeout. The error message is
  misleading — if a Lambda@Edge function exceeds its configured timeout, CloudFront reports a
  permissions-sounding 503, not a timeout error.
